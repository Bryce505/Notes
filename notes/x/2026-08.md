## Graph Engineering: Stop Chaining Your Agents
- **剪藏**：2026-08-25 18:44 ｜ **发布**：2026-08-14
- **优先级**：高 ｜ **状态**：未读
- **关键词**：Agent工作流 / 图结构 / 并行化 / 数据契约 / Claude Code / 动态工作流
- **摘要**：文章尖锐批评多步 Agent 最常见的实现是串行队列——步骤间实际没有数据依赖却互相等待，浪费资源。作者提出用图结构设计 Agent 工作流：节点是工作单元，边是数据依赖，通过数据契约、并行扇出、汇聚、条件路由和验证器等手段优化。以 Claude Code 动态工作流为例，给出 14 步路线图，包括用 parallel() 并行执行、用 pipeline() 替代 barrier、让模型分层以控制成本、用代码而非对话做编排等。核心观点是 Agent 上限不在模型而在工作拓扑，图形化编排能极大提升速度、可靠性和可扩展性。文末提供六种可直接套用的图模式，如安全扫描、深度研究、差异审计等。
- **洞见**：
  - 线性脚本是退化的图，砍掉不传数据的箭头即可发现可并行节点，大幅提速。
  - 并行扇出与汇聚组成的菱形拓扑是复杂 Agent 的基础，可适配多种任务。
  - 编排层应用代码而非模型对话实现，使多子代理协调的 token 成本趋近于零。
  - 默认使用 pipeline() 流式处理而非 barrier 全量等待，能显著降低延迟。
- **是否值得读**：提供了从思维转变到具体可操作的完整方法，信息密度高，观点反直觉且可迁移性极强。

- **剪藏**：2026-08-25 18:15 ｜ **发布**：2026-08-24
- **优先级**：高 ｜ **状态**：未读
- **关键词**：Agent Swarm / 上下文图 / 强化学习 / 任务分解 / 多智能体协同 / Kimi K3
- **摘要**：本文介绍 Moonshot AI 的 Kimi K3 Agent Swarm 功能，指出并行运行300个智能体只是容易的一半，真正的难点在于如何将分散的结果连接成有价值的上下文图。Agent Swarm 通过编排器动态创建无预定义角色的子代理，并利用强化学习训练分解行为，而非静态模板。作者以收集200余篇散落文章为例，说明宽任务适合并行，但判断类步骤仍需串行。文章强调该功能适用于宽而重复的任务，且消耗的积分是常规任务的数倍，因此需权衡是否值得。结论是，巨额智能体数量并非卖点，无需手动设计团队且输出统一才是核心价值。
- **洞见**：
  - 并行运行数百个代理并不难，真正的价值在于如何将分散的结果整合成有联系的上下文图。

  - 该功能适合‘宽而重复’的任务，对于需要深度思考的单一任务反而增加无谓成本。
  - 在使用 swarm 前应判断任务是否真正需要并行，否则只是用更多积分得到相同答案。
- **是否值得读**：文章提出‘上下文图’这一独到概念，深入剖析了多智能体系统的核心瓶颈与成本权衡，具有参考价值。
