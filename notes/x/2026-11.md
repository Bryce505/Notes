- **摘要**：作者对比 Lauren Tan 的自动化入门指南（把人的最佳实践教给 Grok bot，让它像自己一样思考），提出自己的做法：更相信模型能力，只定目标和验收标准，少干涉中间步骤，形成「目标→验收→改进」的循环。具体做法：讲清目标；可选地给出验收标准，并配上验收工具（截图、联网检索、代码运行环境）。例如做新闻发布自动化时，动笔前必须先做事实核查。先让 Agent 跑一遍再调整；调整前自己要能判断好坏并把问题描述清楚。还要让 Agent 自我进化：把打磨好的做法趁热沉淀成 Skill，每轮往 lessons.md 记教训，让模型自行决定是否优化 Skill，并定期重构去臃肿、重跑测试集防回退。
- **洞见**：
  - 与其教 Agent 照搬人的最佳实践，不如只定目标和验收标准，把执行细节交给模型；模型越强，这种做法越省心。
  - 关键是「先跑一枪」：先有产出才有可优化的偏差，看靶心比看执行过程更有价值。
  - 真正的门槛在验收环节——你得自己知道什么是好的，并能把差距准确描述给 AI。
  - 让 Agent 在任务现场把成功经验沉淀成 Skill、把教训写进 lessons.md，可绕开会话记忆丢失的问题；代价是 Skill 臃肿，需定期重构并回归测试。
- **是否值得读**：给出了可直接照搬的 Agent 自动化工作流（目标—验收—沉淀—重构）及具体工具与案例，并与另一套方法论对比，信息密度高、可操作性强。

## 开了 TUN 就是全局？一文讲清代理软件的「规则、全局、系统代理、TUN」（附最佳实践）
- **剪藏**：2026-11-18 05:43 ｜ **发布**：2026-11-17
- **优先级**：高 ｜ **状态**：未读
- **关键词**：TUN 模式 / 系统代理 / 分流规则 / 全局模式 / 链式代理 / 静态住宅 IP
- **摘要**：作者从自己踩坑出发，拆解代理软件四个概念：系统代理只对会读取系统设置的软件（如浏览器）生效；TUN 通过虚拟网卡接管整机所有流量；「规则／全局／直连」才决定流量走节点还是走本地。核心结论是：开 TUN 不等于全局，TUN 只负责接管，走向仍由分流模式决定。最佳实践是系统代理与 TUN 同时开启、分流选规则——浏览器走系统代理便于按域名匹配规则，终端和 AI 客户端靠 TUN 接管。作者还建议把 Claude、Codex 等走「机场节点＋静态住宅 IP」链式代理，因静态 IP 带宽约 20Mbps，不适合刷视频，并附给 Agent 的配置提示词与验收步骤。
- **洞见**：
  - TUN 与「全局」是两个维度：前者决定谁被接管，后者决定流量往哪走，混为一谈是常见误区。
  - 系统代理和 TUN 应同时开：浏览器直接把域名交给代理软件，省去先解析成 IP 再还原域名的环节，分流更准且不会重复代理。
  - Claude Code、Codex、Cursor 等桌面与命令行客户端不读系统代理，只开系统代理必然超时，必须靠 TUN 接管。
  - AI 流量走机场节点再接静态住宅 IP、视频走普通节点，是在固定身份需求与静态 IP 带宽上限（约 20Mbps）之间的折中。
- **是否值得读**：把常被混淆的四个概念拆成「接管开关＋分流模式」两组，并给出可直接照做的配置、分层流量方案和 Agent 提示词，信息密度与可操作性都高。
- **链接**：[原文](https://x.com/longhaiqwe123/status/2122568684312940870?a=-H4HGUPb5tt5Xk6T298&s=19) ｜ [全文快照](../../archive/x/2026-11/%E5%BC%80%E4%BA%86_TUN_%E5%B0%B1%E6%98%AF%E5%85%A8%E5%B1%80%EF%BC%9F%E4%B8%80%E6%96%87%E8%AE%B2%E6%B8%85%E4%BB%A3%E7%90%86%E8%BD%AF%E4%BB%B6%E7%9A%84%E3%80%8C%E8%A7%84%E5%88%99%E3%80%81%E5%85%A8%E5%B1%80%E3%80%81%E7%B3%BB%E7%BB%9F%E4%BB%A3%E7%90%86%E3%80%81TUN%E3%80%8D%EF%BC%88%E9%99%84%E6%9C%80%E4%BD%B3%E5%AE%9E%E8%B7%B5%EF%BC%89-940870.md)

- **剪藏**：2026-11-01 22:10 ｜ **发布**：2026-11-01
- **优先级**：中 ｜ **状态**：未读
- **关键词**：Claude 使用教程 / 链式代理 / 静态 IP / 网络代理配置 / 谷歌商店订阅
- **摘要**：作者分享自己在中国大陆使用 Claude 的整套办法：机场出境后，接入一个台湾独享静态 IP，做链式代理，让 Claude 只看到这个固定出口；再配合谷歌邮箱、指纹浏览器、系统时区和谷歌商店付款。他解释了原理：机场是多人共用 IP，一旦被封换节点也没用；静态 IP 独享但无法直接出网，须挂在机场后面，且地区须与机场一致以免高延迟（实测台湾 44 毫秒、美国 300 多毫秒）。文中给出 1024proxy 采购、用 Clash Verge Rev 配置、用 ip.net.coffee 验证、买或自注册谷歌号时注意更换密码，以及绑定国内 VISA 卡、填美国免税州账单地址。作者也承认，虚拟标注为“家庭IP”的 IP 被查出来是机房 IP，通过谷歌商店多付 50 美元相当于为可能的封号买保险，且全程不保证不封号、不保证不亏钱。
- **洞见**：
  - 机场共享 IP 一旦被封，换别的节点也没用；真正能防封的是独享且固定的出口 IP。
  - 光有静态 IP 不够，它本身出不了海；必须接在机场后面做链式代理，且两边选同一地区，否则延迟从几十毫秒涨到几百毫秒。
  - 封号不只取决于 IP，还包括时区、浏览器指纹等环境一致性；IP 只是其中一小部分。
  - 用谷歌商店订阅比官网贵约 50 美元，但被封后可向谷歌申诉退款，相当于为风险买保险。
- **是否值得读**：属步骤具体、可直接照做的操作指南，但夹带返利链接、依赖灰色服务，且作者自认效果与合规风险都不保证，适合有需要时参考而非精读。
