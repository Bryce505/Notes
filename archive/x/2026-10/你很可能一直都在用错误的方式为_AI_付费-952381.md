# 你很可能一直都在用错误的方式为 AI 付费

- 发布时间：2026-09-01

20 美元的订阅很少会让人觉得贵。但四个这样的订阅，很容易在不知不觉中变成每年 1000 美元的习惯性支出，即使你真正频繁使用的只有其中一半。

现在最容易在 AI 上花过头的方法，恰恰也是看起来最合理的方法：每当一个产品变得有用，就订阅它。

ChatGPT Plus 每月 20 美元。Claude Pro 又是 20 美元。SuperGrok 30 美元。Cursor Pro 20 美元。四个全订，每月就是 90 美元，一年 1080 美元，还没算税。单独看，每个订阅都不算特别贵，而且在你点击订阅时，每一个都很容易找到合理的理由。问题只有在它们开始叠加之后才会显现出来。

它们之间的功能重叠也在不断增加。8 月 26 日，xAI 宣布 Grok Bot 现在已经包含在 Cursor Pro 以及更高级别的 Cursor 套餐中。Cursor 当前的 Pro 套餐也宣传提供前沿模型访问以及较高的 Grok 使用额度。这并不意味着 SuperGrok 没有价值 - SuperGrok 仍然有自己的 Grok 配额、Imagine 功能、连接器以及其他产品权益 - 但如果一个人同时为两者付费，至少应该检查一下自己是否正在为同样的东西付两次钱。

这正在变成一个普遍问题。AI 市场正在走向功能越来越重叠的套餐，而模型本身的访问方式却越来越容易单独购买。过去你可能必须订阅整个产品才能使用某个模型，现在它可能已经可以通过 API、IDE、模型网关，或者你已经订阅的另一个产品来使用。

这改变了个人 AI 工具栈的经济逻辑。

真正有用的问题已经不再只是：“哪些 AI 订阅值得每月 20 美元？”而是：你只是偶尔想使用的每一个模型，真的都值得永久出现在每个月的账单上吗？

第一部分 - 四个小订阅，加起来就是一笔很大的年度支出

周期性付款很擅长隐藏真实的使用频率。

一旦 ChatGPT Plus 在月初完成扣费，这个月打开 ChatGPT 50 次还是 500 次，在财务感受上几乎没有区别。这正是订阅制本来要做的事情：拿掉计价器，让你在使用产品时不必考虑每一次请求的成本。

对于一个你每天都在使用的产品来说，这可能非常划算。

问题从第二个、第三个和第四个订阅开始。大多数人不会以同样的强度使用四个 AI 产品。他们可能每天工作都待在其中一个产品里，用另一个写代码，在某个特定模型更适合某项任务时才打开第三个，而第四个则只是一直留着，因为他们不想失去访问权限。

计费方式把四个产品都当成永久工具。但真实的使用行为，可能更接近两个永久工具加两个偶尔租用的模型。

如果你几乎每天都使用 Claude，那么一年 240 美元可能很容易解释。但如果你一个月只打开两次，只因为偶尔更喜欢 Sonnet，那么同样的 240 美元买到的实际价值就完全不同。

Grok 也是一样。想试 Grok 4.6 时，30 美元听起来不算多。一年下来，它变成了 360 美元。如果 Grok Bot、Imagine、X 搜索以及产品里的其他功能都是你工作流的核心，那这笔钱可能仍然很便宜。但如果你真正想要的只是偶尔能使用 Grok 4.6，那么还有另一种购买这种访问权限的方式。

第二部分 - 先把产品和模型分开

在取消任何东西之前，先弄清楚这个订阅到底买的是什么，会很有帮助。

ChatGPT Plus 并不是一包预付的 OpenAI API Token。它买的是 ChatGPT 这个产品，包括比免费版更广泛的模型和工具访问、文件分析、图像生成，以及在可用情况下提供的研究功能。OpenAI 明确将普通 API 使用单独计费。

Claude Pro 的逻辑类似。20 美元的订阅买的是 Claude 应用本身，以及 Claude Code 和 Cowork 的使用权限；Claude Console 的 API 使用仍然需要单独付费。

Cursor 把这个区别体现得更明显，因为很多人付费的真正原因，是模型周围的整个环境。你得到的是编辑器、Agent 集成、Cloud Agents、Bugbot、Grok Bot 访问以及其他开发工具。用一个 API Key 替代 Cursor，只能替代这个产品中的一部分。

这样一来，我们就有了一种更清晰的方式来审计自己的 AI 工具栈。

当你真正依赖的是产品周围的功能时，订阅最容易被证明是合理的。你每天都使用这个 IDE，把持续性的工作交给 Bot，依赖某个研究界面，经常使用连接器，或者你在某个 AI 助手里待的时间足够长，以至于不想每次调用都去考虑计费。

偶尔访问某个模型则是另一回事。如果你真正想要的只是，在某项任务刚好适合 Sonnet、Grok 或 GPT-5.6 时能问它一个问题，那么你买的本质上是计算资源。而计算资源越来越可以只在实际消耗时购买。

人们之所以会形成昂贵的 AI 工具栈，往往就是因为把这两种东西当成了同一件事。

他们先因为需要某个产品而订阅一个服务，然后又因为想保留对另外三个模型的可选访问权限，再订阅三个服务。

第三部分 - 20 美元到底能买到多少模型使用量？

以现在的 API 价格，这件事已经值得算一遍，而不是靠猜。

假设一个次要模型在一个月里接收 500 万输入 Token，并生成 100 万输出 Token。

按照当前标准文本价格，计算结果大概是这样：

[图片]

GPT-5.6 Sol 当前在促销价格下，每百万输入 Token 为 4 美元，每百万输出 Token 为 20 美元，促销至少持续到 11 月 21 日。Terra 的价格是 $2/$12，Luna 是 $0.20/$1.20。Claude Sonnet 5 是 $2/$10。Grok 4.6 在 Prompt 保持低于 200K 长上下文计费门槛时，价格是 $2/$6。

这张表不应该被理解为模型质量比较。不同供应商对同一份材料的 Token 切分方式不同，尤其是 Claude Sonnet 5 使用了新的 tokenizer，Anthropic 表示，同样的文本相比 Sonnet 4.6 及更早版本大约会产生 30% 更多的 Token。工具、搜索、图片以及 Agent 的行为也可能显著改变最终账单。

真正有用的是这里的数量级。

500 万输入 Token 加 100 万输出 Token，对于一个你认为只是次要模型的工具来说，已经是相当可观的使用量了。在 Claude Sonnet 5 上，这个使用量刚好达到约 20 美元的基础文本费用。如果你的实际使用量大约只有这个工作负载的五分之一，对应的基础成本大约只有 4 美元。

同样按五分之一计算，只要还处于短上下文价格范围内，Grok 4.6 大约是 3.20 美元。

现在，把这些数字和每个月固定支付 20 或 30 美元放在一起比较，不管你这个月打开那个产品两次还是两百次。

这并不能证明 API 永远更便宜。重度用户完全可能很快烧掉 20 美元的 API 使用量，尤其是长时间运行的 Agent 会生成大量输出，或者反复携带巨大的上下文。它真正说明的是，很多人可能从来没有真正计算过盈亏平衡点。

他们把“每月 20 美元”和“每百万 Token 2 美元”看成两个完全不同的计费系统。

实际上，它们只是两种为部分重叠能力付费的方式。

第四部分 - 更实用的配置，往往是一个永久工作流加一个浮动模型预算

假设文章开头那个每月 90 美元的工具栈，属于一个大部分时间都在 ChatGPT 里工作、同时用 Cursor 开发软件的人。Claude 对某些写作和编程任务很有用。Grok 对另外一些任务很有用。但后两者都不是每天使用的工作环境。

没有什么强理由要求这四种关系全部都必须是订阅。

一种可能的配置是保留每月 20 美元的 ChatGPT Plus 和每月 20 美元的 Cursor Pro。然后，不再固定支付另外 50 美元的 Claude 和 Grok 订阅，而是拿出 20 美元作为灵活的 API 预算。

每月支出从 90 美元降到 60 美元。

每年支出从 1080 美元降到 720 美元。

差额是 每年 360 美元。

这 20 美元的浮动预算完全可以这个月全部花在 Claude 上，下个月全部花在 Grok 上。也可以分给五个供应商，甚至几乎完全不用。支出跟着工作负载走，而不是跟着你想保留多少家模型公司的访问权限走。

对于实际上只需要一个原生产品的人来说，差距还可能更大。一个 20 美元订阅，加上 20 美元 API 预算，每月总预算就是 40 美元。和最初每月 90 美元的工具栈相比，一年可以少花 600 美元。

这些数字只是示例，而不是固定建议。一个重度 Claude Code 用户完全可能值得额外保留 Claude Pro。大量使用 Grok Bot 的人，可能从 SuperGrok 获得更好的经济性。一个靠写代码工作的人，可能会认为 Cursor 是整个工具栈里最后一个愿意取消的订阅。

混合模式的重点在于：每一个订阅都必须单独证明自己值得成为长期固定支出。

随着产品开始打包彼此的功能，这一点会变得更加重要。比如 Cursor Pro 现在已经包含 Grok Bot，所以如果某个人最初订阅 SuperGrok 的一部分原因就是为了 Bot 访问，那么现在就有了重新检查功能重叠的理由。这个市场变化得足够快，以至于三个月前合理的工具栈，即使用户什么都没做，也可能慢慢积累出重复支出。

第五部分 - 一旦开始按 Token 付费，你就会开始看见钱到底花在哪里

把一部分工作切换到 API 计费，还有另一个效果：低效行为不再是隐形的。

订阅制会让你习惯用 Prompt 来思考。按量计费会迫使你开始考虑，每个 Prompt 到底反复携带了什么东西。

假设一个 Coding Agent 正在处理一个大型代码库。它的请求可能反复包含项目说明、架构文档、工具定义、编码规范，以及大量没有发生变化的源码。如果连续 50 次请求都附带 100,000 个稳定不变的 Token，那么一个最简单的实现可能会反复为几乎相同的信息支付处理费用。

提示词缓存就是为这种工作负载存在的。

Claude Sonnet 5 当前普通输入价格为每百万 Token 2 美元。五分钟缓存写入的价格是每百万 2.50 美元，而缓存命中的价格是 0.20 美元。Anthropic 将缓存读取描述为普通输入价格的 10%。第一次写入更贵，但当稳定前缀被反复使用时，成本会显著下降。

GPT-5.6 采用类似的经济结构。Sol 当前每百万普通输入 Token 为 4 美元，缓存输入为 0.40 美元；Terra 是 2 美元对 0.20 美元；Luna 是 0.20 美元对 0.02 美元。OpenAI 对 GPT-5.6 的缓存写入按照普通输入价格的 1.25 倍收费，而读取则享受缓存输入 90% 的折扣。

因此，一个 Agent 完全可以在不换成更弱模型的情况下大幅降低成本。模型没变，任务没变，可复用的上下文也没变。你只是停止了每次遇到同样的内容时，都重新支付完整的“阅读”价格。

还有第二种更容易理解的折扣：速度。

大量 AI 工作并不需要在人盯着屏幕的时候完成。如果你要分类 50,000 条客服消息、隔夜处理一个归档、运行评测，或者从大型文档集合中提取结构化信息，结果通常完全可以晚一点到。

Anthropic 的 Batch API 收取 标准 API 价格的 50%。截至目前，Sonnet 5 的 Batch 价格是每百万输入 Token 1 美元、每百万输出 Token 5 美元，而标准价格是 2 美元和 10 美元。

这是一个非常清楚的例子，说明为什么只比较模型首页上的 API 单价，会错过很大一部分真实成本结构。同样一个 Sonnet 5 工作负载，最终账单可能因为上下文是否被缓存，以及结果是否必须同步返回，而出现很大差异。

第六部分 - 长上下文，是一个便宜工作流悄悄变贵的地方

下一个成本问题通常会在 Agent 已经运行一段时间之后出现。

一段最开始只有很短 Prompt 的对话，会逐渐积累终端日志、代码、工具输出、之前犯过的错误、浏览器结果以及大量文档。现代模型可以接受巨大的上下文，因此最简单的实现方式就是不断把所有东西一起往后带。

模型能够接受巨大上下文，并不意味着每一次请求都应该使用它。

Grok 4.6 是一个很好的例子。当 Prompt 低于 200,000 Token 时，它的价格是每百万输入 Token 2 美元、缓存输入 0.50 美元、输出 6 美元。一旦 Prompt 达到 200,000 Token，它的长上下文价格变成 4 美元、1 美元和 12 美元。xAI 明确说明，一旦跨过这个门槛，长上下文价格将应用于整个请求里的所有 Token。

GPT-5.6 也有自己的门槛。OpenAI 表示，当 Prompt 超过 272,000 个输入 Token 时，整个请求的输入价格会变成 2 倍，输出价格变成 1.5 倍。

这产生了一个有些奇怪的激励：供应商正在竞争谁能提供更大的上下文窗口，而高效用户反而需要越来越谨慎地选择，到底应该把什么放进这些窗口里。

当任务确实需要时，100 万 Token 的上下文非常有价值。但如果一个 Agent 只是因为没人决定清理，而一直拖着 40 分钟前早已过时的终端输出继续运行，那么这种长上下文就会变得非常昂贵。

因此，长期运行的 Agent 需要某种形式的记忆管理纪律。旧交互可以被压缩。稳定材料可以被缓存。大型文档集合可以在相关时再检索，而不是永久附加。日志可以被总结。已经完成作用的工具结果可以从活跃 Prompt 中移除。

这没有选择最新的前沿模型那么吸引眼球，但它对账单的影响可能更大。

一个上下文管理糟糕、不断重复携带巨大历史的便宜模型，完全可能比一个经过仔细路由的昂贵模型更贵。

第七部分 - 下一笔节省，来自不再让最强的模型处理最简单的工作

订阅习惯在 API 这边也有一个对应版本：一旦有人选定了最喜欢的前沿模型，就会把所有事情都发给它。

困难的架构决策？前沿模型。

从文档里提取日期和发票编号？还是同一个模型。

调试 race condition？还是同一个模型。

把 20,000 条商品记录转换成固定 JSON 格式？还是同一个模型。

这样做很方便，因为只需要维护一个系统。但如果是处理大量常规任务，这也是一种非常昂贵的方式。

当前 OpenAI 的价格很能说明这个数量级。GPT-5.6 Sol 每百万输入 Token 4 美元、每百万输出 Token 20 美元。GPT-5.6 Luna 则是 0.20 美元和 1.20 美元。输入价格相差 20 倍，输出价格大约相差 16 倍。

这绝不意味着 Luna 和 Sol 可以互换。它们本来就是刻意区分的不同档位。真正有用的结论是：如果一个工作流里有 20 种不同类型的任务，大概率没有必要把这 20 种任务全部分配给同一个模型档位。

提取、分类、格式化、基础总结、直接转换和第一轮筛选，都可以先在便宜模型上测试。困难情况再升级到更强的模型。一个 Coding Workflow 可以把最昂贵的推理留给架构设计、困难调试或者模糊的代码审查，同时把重复性操作路由到别处。

这样一来，真正重要的成本指标就变成了 每一件成功完成的工作需要多少钱，而不是每个 Token 多少钱。

一个便宜十倍的模型，如果需要四次重试和人工修复，最终反而可能输掉这场比较。一个前沿模型如果一次就能解决任务，可能才是更便宜的选择。唯一能知道答案的方法，是测量整个工作流，而不是盯着价格表。

所以，我不会建议围绕“哪个模型最便宜？”这个问题搭建个人 AI 工具栈。

更好的问题是：“我的哪些工作，一旦换到低一个档位的模型，质量才会真正变差？”

这个实验可能比取消一个 20 美元订阅省下更多钱。

第八部分 - 在改任何东西之前，先做一次 30 天审计

大多数人不需要复杂的 Token Dashboard 才能找到明显的浪费。他们真正需要的，只是认真观察一个月。

对于每一个订阅，简单记录你大概多久打开一次，以及你从中需要什么。区分产品功能和模型访问，比精确统计 Prompt 数量更重要。如果你反复使用 Claude Code、Grok Bot、Cursor 的编辑器集成或者 ChatGPT 的原生工具，那么这个订阅提供的价值，并不是简单比较 API 单价就能完全体现的。

如果你一个月只打开某个服务四次，而且这四次全部只是普通文本 Prompt，本来完全可以直接发给底层模型，那么比较就会容易得多。

然后，用按量计费的方式测试这些偶尔使用的工作负载一个月。

你可能会发现，那个“不可缺少”的第二订阅，其实只相当于每月 3 美元的 API 使用量。也可能发现完全相反的情况：API 计费器三天就跑到了 25 美元，这时原来的订阅反而显得非常合理。

两种结果都有价值，因为你终于开始把价格和自己的真实行为进行比较。

同样的审计也应该寻找技术层面的浪费。如果一个巨大的稳定 Prompt 出现在 Agent 的每一轮调用中，测试缓存。如果任务可以隔夜完成，测试 Batch。如果上下文经常跨过 200K 或 272K Token，检查它为什么一直在增长。如果前沿模型正在处理成千上万次确定性的转换，先在便宜模型上抽样测试，再测量失败率。

30 天之后，你的工具栈应该会更容易理解，因为每一笔周期性付款都应该有一个明确的理由继续存在。

个人 AI 工具栈，正在越来越像基础设施

几年前，订阅多个 AI 产品，是保持访问最佳模型的一种简单方式。现在，市场已经复杂得多。

模型访问正在不同产品之间扩散。Cursor 现在包含 Grok Bot。API 可以直接提供前沿模型和廉价模型档位。提示词缓存可以大幅降低重复输入的价格。批处理可以把异步 Claude 工作负载的成本砍半。巨大的上下文窗口带来了自己的价格门槛。便宜模型也已经足够强，可以吸收越来越多的常规工作。

因此，高效的个人 AI 工具栈，很可能不会是“喜欢哪家公司的模型，就订阅哪家公司”。

对很多人来说，它会更不对称：一个每天都在使用的产品，也许再加一个真正依赖的专业环境，然后在后台配一个可以灵活分配的按量预算。

这样的配置也更能承受模型快速迭代带来的变化。

如果下个月另一家供应商发布了最适合你某一部分工作的模型，你不需要再增加一个每月 20 或 30 美元的永久订阅。只需要把一部分支出路由过去。如果后来它不再有用，那部分支出也会随之停止。

如果 AI 工具每月为你节省的时间或者增加的收入远远超过 100 美元，那么每月花 100 美元完全没有问题。一个每天都在多个产品里工作的专业用户，完全可能合理地保留所有订阅。

真正的浪费出现在这样一种情况：一笔周期性付款之所以继续存在，仅仅因为取消它让人感觉像是失去了访问权限。

API 定价已经改变了这笔账。在很多情况下，你已经不需要在“永久拥有访问权限”和“完全没有访问权限”之间二选一。你可以让某个模型一直处于可用状态，而不需要一年 12 个月都租下它对应的整个消费级产品。

所以下一次准备增加新的 AI 订阅之前，先看一眼那些已经在从你的银行卡扣钱的服务，然后问一个更具体的问题：

我每个月付钱，是因为我每个月都在使用这个产品，还是因为我只是偶尔想保留使用它背后模型的选择？

这两种用户，本来就不应该用同一种方式为 AI 付费。
