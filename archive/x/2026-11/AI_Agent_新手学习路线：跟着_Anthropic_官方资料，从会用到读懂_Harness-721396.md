Anthropic 这家公司，我是真的不喜欢。

动不动就封号，动不动就限制使用，Claude Code 好用归好用，用着用着心里总悬着一块石头。

但是有一件事我不得不承认：它写的东西是真的好。

前段时间我在 X 上推荐了 Anthropic 官方的 5 篇 Agent 入门文章，没想到大家反馈都特别好，收藏直接破了一千。后来我又顺手补了一条，把它的 8 个学习网站也整理了出来。

但是清单发出去以后，我自己回头看，问题其实挺明显的：五篇文章、八个网站，再加上官方博客里几十篇技术文章，一个新手拿到这张清单，大概率还是不知道该从哪篇开始读。读到一半看不懂，最后就是收藏吃灰。

所以这篇我不打算再列清单了，而是把这些资料排好顺序：先读什么、读到哪就够了、读完能做到什么。

如果你只有 5 分钟，先记住这三件事：

分三层读：先学会用，让 Agent 稳定帮你干活；再学会搭，搞懂 Agent 是怎么拼起来的；最后读懂 Harness，明白为什么同一个模型，换个外壳效果差这么多；

学方法，别抄产品：这些资料讲的是通用方法，换成 Codex、Pi、DeepSeek Harness 一样成立；但是里面提到的具体功能很快会过时，别照搬；

每读一层，就动手做一件事：写一份项目说明、写一个 Skill、给长任务加一个进度文件。只读不做的话，一个月后基本就忘干净了。

一、为什么学 Agent，我推荐 Anthropic 的资料

讨厌归讨厌，我推荐它的资料，理由其实很实际，就三个。

1. 一手资料，写的人就是做 Agent 的人

Anthropic 的 Engineering 博客，开头就写得很清楚：这个团队负责让 Claude 稳定可靠运行的基础设施，同时把他们在构建、评估和部署大规模 AI Agent 时学到的东西分享出来。

[图片]

说白了，你读到的不是别人的二手解读，而是做 Claude Code 的那批工程师，直接把自己踩过的坑和总结出来的方法写给你看。哪些做法有效、哪些是坑、改了一个设计之后效果变了多少，很多文章都直接给了具体数字。

2. 讲的是通用方法，不只适用于 Claude

这一点其实是我最看重的。

上下文怎么管、工具怎么设计、Skill 怎么写、长任务怎么才不跑偏，这些问题根本不是 Claude 独有的。我自己前前后后折腾过 Pi Agent、DeepSeek Harness、Claude Code、Codex，还有 Hermes Agent，实际用下来，几乎每个工具里都能碰到同样的问题，解法也大同小异。

所以就算你哪天被封号了、不再用 Claude 了，这些资料照样值得读。学的是方法，工具随时都可以换。

3. 免费，而且一直在更新

所有资料都是免费公开的。而且 Engineering 博客今年一直在更新：3 月出了一篇讲长任务的 Harness 设计，11 月又刚出了一篇讲 Agent 记忆，这两篇第五章都会讲到。

三、第一层 · 会用：先让 Agent 稳定帮你干活

这一层的目标其实很简单：让 Agent 少犯错，犯了错你能第一时间发现。

很多人觉得 Agent 不好用，问题往往不在模型，而是你没告诉它该知道的事，也没给它检查结果的办法。

1. 先看别人拿它干什么

第一篇推荐先读《How Anthropic teams use Claude Code》，2025 年 7 月发布，大概 9 分钟就能读完。

它讲的是 Anthropic 内部各个团队到底怎么用 Claude Code：熟悉陌生代码库、写测试、做代码审查、排查线上故障、做原型、整理文档、搭自动化流程，里面还有不少不写代码的同事的用法。

这篇的价值其实不在技巧，而在于打开思路。很多人用 Agent 只会让它写代码，看完你会发现，能交给它的事情比你想象的多得多。

2. 再读官方最佳实践

第二篇是 Claude Code 官方的《Best practices for Claude Code》。它以前发在 Anthropic 博客上，现在已经搬进了 Claude Code 的文档里。

这篇比较长，不用一口气读完。页面开头第一句话，其实就是整篇的提纲：告诉 Claude 它看不到的东西，给它一个能跑的检查，把没有例外的规则管起来。

[图片]

我建议先把这三节吃透，翻译成普通人能直接上手的动作就是：

第一节：告诉 AI 它看不到的东西（Tell Claude what it can't see）

Agent 能读你的文件，但是它不知道你脑子里在想什么：测试怎么跑、哪段代码的名字起得容易误导、哪些决定根本没写进仓库、哪个错误你已经纠正过它两次了。

这些信息就写进项目说明文件里，Claude Code 里叫 CLAUDE.md，Codex 和 Pi 里叫 AGENTS.md。

官方特别强调了一点：这个文件一定要短。因为它每次对话都会被完整加载，你每多写一行，每个任务都要分一点注意力给它。仓库里本来就读得到的东西不用写，只写它读不到的。官方还说了一句很实在的话：在规则前面加“IMPORTANT”，大概率解决不了问题。

那规则多了怎么办？直接按目录拆开。我自己的知识库就是这么做的：根目录放一份所有地方都通用的规则，每个子目录只写自己特有的那几条，离目标文件最近的那份优先。这样 Agent 写长文的时候，就不会被短视频目录的规矩干扰。

第二节：给它一个能跑的检查（Give Claude a check to run）

这一节我觉得是整篇最重要的。

官方原话的意思是：给它一个能跑、而且结果只有“通过”或“不通过”的东西。可以是一个测试文件、一次构建的退出码、一个代码检查工具、一个对比输出的脚本，甚至是一张和设计稿放在一起对比的截图。

还有一个配套的习惯：让它拿证据，而不是拿结论。它说一句“已经完成”不算数，你要让它把跑了什么命令、命令输出了什么，或者截图，一起交出来。

我之前写 Pi 零基础实操的时候，就专门强调过这一点：任务结束以后，我不会拿 Pi 自己的总结当证明，而是直接回到命令行，检查原文件、输出文件和里面的内容。说实话，Agent 说“完成了”和事情真的完成了，中间经常还隔着一段距离。

第三节：没有例外的规则，交给机制管（Enforce the rules that can't have exceptions）

有些事是绝对不能做的：删数据、推送到生产环境、动某个目录。这类规则别只写在提示词里求它遵守，提示词本质上只是“建议”，模型确实有可能不听。

官方的建议是交给确定性的机制来管：钩子（hooks）、权限规则、沙箱。换到别的工具里，就是权限模式、确认弹窗、只读目录这类设置。

这一层读完，动手做一件事

给你最常用的 Agent，写一份不超过一屏的项目说明。

只写三类内容就行：它读不到的背景信息、测试或检查怎么跑、绝对不能做的事。最后再加一句要求：完成任务以后，把检查命令和输出一起交给你。

写完直接跑一个真实任务，对比一下前后差别有多大。

四、第二层 · 会搭：搞懂 Agent 是怎么拼出来的

会用之后，你迟早会好奇：Agent 到底是怎么工作的？为什么有的任务它做得特别好，有的任务却总是做歪？

这一层要读三篇文章，再配两个动手材料。

1. 《Building effective agents》：先分清 workflow 和 agent

《Building effective agents》是 2024 年 12 月发布的，这篇我前后读过不止一遍，每次重读都会有新的收获。

它先把两个经常被混着用的概念分清楚了：

Workflow（工作流）：步骤是你提前写死的，模型按固定路线走；

Agent（智能体）：模型自己决定下一步做什么、用哪个工具。

这两者的地基其实是同一个东西，文中叫“增强型 LLM”，说白了就是一个加上了检索、工具和记忆的大模型。

在这个地基上，文章总结了 5 种常见的工作流模式，我把它们对应到了日常场景里：

[图片]

这篇文章里我觉得最值得记住的一句建议就是：先用最简单的方案。能用一次调用解决的，就别上工作流；能用工作流解决的，就别上 Agent。只有确实能带来效果的时候，才去加复杂度。

我之前重读这篇的时候，还专门拿它对照过 Pi Agent：Pi 的系统提示词只保留了最基本的内容，默认也只给 4 个基础工具，这种克制和这篇文章的思路几乎完全一致。真正跑得好的 Agent，往往不是框架最复杂的那个。

2. 《Writing effective tools for agents》：工具是写给 Agent 用的

第二篇是《Writing effective tools for agents — with agents》，2025 年 9 月发布。

这篇要解决的问题是：给 Agent 用的工具，和给人用的接口，根本不是一回事。

文章开头有一句话我觉得说得特别准：工具是一种新的软件，它是确定性的系统和不确定的 Agent 之间的一份契约。

我挑了几个最实用的结论：

合并工具，别照搬接口：与其给 Agent“列出用户”“列出日程”“创建日程”三个工具，不如直接给一个“安排会议”。工具拆得越碎，Agent 越容易调错顺序。

按服务给工具起名：比如 asana_search、asana_projects_search，工具一多，Agent 才分得清哪个是哪个。

只返回有用的信息：能返回名字就别返回一串 ID。文中举了个例子，同一个结果的“详细版”要 206 个 token，“简洁版”只要 72 个，差不多只有三分之一。

限制返回的长度：分页、筛选、截断都要做。文中提到，Claude Code 默认会把单次工具返回限制在 25,000 个 token 以内。

报错要能指导下一步：别只返回一句“出错了”，要告诉 Agent 哪里错了、应该怎么改。

像给新同事交代工作一样写工具说明：参数名要写清楚，比如写 user_id，不要只写 user。

最有意思的其实是标题里那半句“with agents”：文章建议先拿一批真实任务来测试工具，再把测试记录交给 Claude Code，让它自己分析问题、帮你改工具。相当于用 Agent 来改进给 Agent 用的工具。

就算你暂时不写工具，这篇也值得读一读。读完再去看各种 MCP 服务，你基本能一眼看出哪些设计得好，哪些装上只会白白占上下文。

3. 《Equipping agents for the real world with Agent Skills》：Skill 怎么写

第三篇讲的是 Skill，《Equipping agents for the real world with Agent Skills》，2025 年 10 月发布。这套格式在 2025 年 12 月已经变成了开放标准，Pi、DeepSeek Harness 这些工具现在也都能识别 Skill。

Skill 的结构其实很简单：一个文件夹，里面放一个 `SKILL.md`。文件开头写上名字（name）和描述（description），下面写具体做法，需要的话还可以附上脚本和参考资料。

它最关键的设计叫“渐进式加载”，一共分三层：

平时只加载名字和描述，占的上下文很少；

用到的时候，才读取 `SKILL.md` 正文；

正文里提到的参考文件和脚本，需要时再读。

这个设计正好解释了我自己踩过的一个坑。今年 4 月我写过一篇文章，讲我在 Claude Code 里前后装了 30 多个 Skill，跑了两个月，最后每天真正在用的只剩 6 个。装得太多，问题就出在第一层：Agent 每次都要把所有 Skill 的描述扫一遍，再决定用哪个，描述一多，它就开始乱选。

所以 Skill 真的不是越多越好，一定要贴着你自己的工作流来装。

文章最后还提醒了一句，我觉得新手一定要记住：Skill 是可以带脚本的，所以只从你信任的来源安装。装一个来路不明的 Skill，就等于让一段陌生代码用你的权限在电脑上跑。

4. 两个动手材料

三篇读完，就可以去两个 GitHub 仓库里动手试试了：

[Anthropic Skills](https://github.com/anthropics/skills)：官方的 Skill 示例库。template/ 是一个 Skill 模板，spec/ 是规范，skills/ 下面按设计、开发、办公文档等分类放着示例。仓库说明里也写得很清楚：这些示例主要用来演示和学习。

[图片]

[Claude Cookbooks](https://github.com/anthropics/claude-cookbooks)：官方的示例代码合集。新手先看 patterns/agents（就是上面 5 种模式的代码实现）和 tool_use（工具调用），其他目录等用到了再看。

顺便说一下 Skill 和 MCP 的区别

很多人一直分不清这两个，其实读完这一层就清楚了：

MCP 给 Agent 接上新能力：读邮箱、查数据库、操作某个网站，这些它本来做不到的事；

Skill 告诉 Agent 怎么做事：一套固定的流程、规范、经验，比如“写周报按这个格式”“发布前检查这五项”。

一个是手，一个是经验。很多场景下两者是一起用的：MCP 负责把数据接进来，Skill 负责规定拿到数据以后该怎么处理。

这一层读完，动手做一件事

把你最常重复交代给 AI 的那件事，写成你的第一个 Skill。

直接照着官方的 template/ 来写，描述里写清楚“什么时候该用它”，正文写清楚步骤和检查标准。写完开一个新对话测试一下，看 Agent 能不能在该用的时候自己用上它。

五、第三层 · 读懂 Harness：为什么同一个模型，换个外壳效果差这么多

[图片]

这一层是全文的重点，也是我最近研究最多的方向。

先说 Harness 到底是什么。打个比方：模型是大脑，Harness 是身体。Harness 负责把模型接到文件、终端、浏览器和各种工具上，管理对话历史、权限确认、上下文压缩，最后再把结果交还给你。Claude Code、Codex、Pi、DeepSeek Harness，本质上都是 Harness。

折腾了这么多 Agent，我越来越觉得：模型之间的差距在缩小，真正拉开差距的是 Harness。同一个模型，放进不同的 Harness 里，实际用下来效果可能差很多。

一个 Harness 到底好不好，我主要看三件事：

上下文管理与压缩：对话越来越长，怎么保证模型还能看清重点；

长任务执行与异常恢复：任务一跑就是几个小时，中途断了、跑偏了，怎么接着干；

结果验证：怎么确认它真的做对了，而不是它自己“觉得”做对了。

刚好 Anthropic 有四篇文章，把这三件事讲得很透。

1. 《Effective context engineering for AI agents》：上下文是有限的注意力

第一篇是《Effective context engineering for AI agents》，2025 年 9 月发布。

文章提出了一个概念，叫上下文工程，可以理解成提示词工程的升级版。提示词工程只关心你写的那段话，上下文工程关心的则是模型每一次看到的全部内容：系统提示、工具定义、对话历史、读进来的文件，等等。

为什么要关心这个？因为上下文越长，模型的表现反而越差，文中把这个现象叫“上下文腐烂”（context rot）。模型的注意力是有预算的，塞进去的东西越多，每样东西分到的注意力就越少。

文章给的办法，我归纳成了四条：

系统提示写在“合适的高度”：不要写成一堆死板的条件判断，也不要空泛到没有任何信息量；

工具集保持精简：功能重叠的工具，只会让模型犹豫；

需要时再取：不把所有资料一次性塞进去，而是让 Agent 需要的时候自己去查；

长任务的三个办法：压缩（把旧对话总结成摘要）、结构化笔记（让 Agent 自己记笔记，需要时再读）、子 Agent（让子 Agent 去干脏活累活，只把结论交回来）。

如果你想把“压缩”这件事看得更具体一点，可以接着读我之前翻译的 Pi 官方文章《从零开始理解上下文压缩》，里面把 Pi 什么时候触发压缩、那份“交接简报”怎么写，都讲得很细。

2. 《Effective harnesses for long-running agents》：让 Agent 像工程师一样交接班

第二篇是《Effective harnesses for long-running agents》，2025 年 11 月发布。

它要解决的问题是：一个任务大到一次对话根本做不完，得分很多轮才能完成，那怎么保证每一轮都能接得上？

文章给的办法，其实很像一个真实的工程团队：

先派一个“初始化 Agent”把环境搭好：写一个启动脚本，建一个进度记录文件，做一次初始的 git 提交；

之后每一轮，“编程 Agent”只推进一个功能：开工前先读进度记录和 git 历史，搞清楚上一轮做到哪了；

用一份 JSON 格式的功能清单，记录哪些功能做完了、哪些还没做；

每做完一步就提交到 git，出了问题随时能退回去；

用端到端的浏览器测试来确认功能真的能用，而不是看代码“好像没问题”就算完。

这篇文章最值得学的，其实不是那些具体的文件名，而是背后的思路：别指望 Agent 记住一切，把状态写进文件里。进度文件、功能清单、git 历史，就是 Agent 的交接本。

而且这个办法不只适用于写代码。你让 Agent 写一个系列教程、整理一大批资料，都可以照着来：先让它建一份清单，每次只做一项，做完就更新清单。

3. 《Harness design for long-running application development》：每个组件都是一个假设

第三篇是 2026 年 3 月发布的《Harness design for long-running application development》，可以看成上一篇的进阶版。作者让 Agent 从一句话需求出发，连续跑了几个小时，最后做出了一个完整的应用。

文章里有几个发现，我读完觉得特别有启发：

第一，模型会有“上下文焦虑”。上下文快满的时候，有的模型会急着收尾，活还没干完就说做完了。文中提到 Sonnet 4.5 这个问题特别明显，到了 Opus 4.5 基本就没有了。

第二，Agent 评价自己的作品，总是偏高。所以作者干脆把“干活的”和“检查的”拆成了两个 Agent：一个负责生成，一个负责评估。评估 Agent 会真的打开网页去点、去试，而且还要专门调教它，让它挑剔一点。

第三，开工之前，先约定好“做完”到底是什么意思。每一轮开始前，干活的 Agent 和检查的 Agent 会先就验收标准达成一致，写成文件，最后就按这个文件来验收。

第四，好的 Harness 确实很贵，但是值。文中做了一个对比：同一个需求，单个 Agent 跑 20 分钟、花 9 美元；完整的 Harness 跑了 6 个小时、花了 200 美元，但是做出来的东西要完整得多。

不过整篇文章最打动我的，是结尾提到的一个原则：

每一个 Harness 组件，都代表了一个假设：模型自己做不到这件事。

所以每次模型升级以后，都要回头把这些组件一个个检查一遍，看哪些已经多余了。作者自己就是这么做的：换到 Opus 4.6 以后，他直接拿掉了原来分轮次推进的结构，评估也从每轮一次改成了最后只做一次，规划和评估这两个角色则保留了下来。

这其实也解释了，为什么我一直觉得 Harness 是最值得深入研究的方向：它不是一次写好就完事的东西，而是要跟着模型能力一起不断调整的。

4. 选读：《The components of agent memory》：记忆不是记得越多越好

第四篇是 2026 年 11 月刚发布的《The components of agent memory》，讲的是 Agent 的记忆。这篇算选读，但是如果你被 Agent 的记忆功能折腾过，我强烈建议读一读。

[图片]

文章先给记忆下了一个定义：Agent 从经验里学到、并且能跨会话保留下来的知识。然后把它分成了四层，从下往上依次是：

对话记录：完整的事件日志，可以搜索；

记忆笔记：Agent 自己写的笔记；

记忆整理：比如把笔记整理成一份知识库；

注入上下文：每次会话开始时都会加载的那一小部分。

关键在最上面那一层：它必须足够小。文中提到，Claude Code 的自动记忆，只会加载 MEMORY.md 的前 200 行或者前 25KB。

还有一个挺反直觉的结论：告诉 Agent 记忆是用来干什么的，但是别规定它怎么记。文中专门做过测试，给模型定一条死规定，比如“只记录失败”，较新的模型记忆效果反而变差了。

读到这里我真的很有共鸣。今年 6 月我直接把 Claude Code 的自动记忆关掉了，原因就是记忆点越攒越多，三十几条全部塞进每次会话，长文的规矩和短视频的规矩开始互相打架。现在回头看，问题正好就出在最上面那一层：该小的地方没有小，该分开的地方也没有分开。

《从零开始理解提示缓存》：为什么同样的对话，有时候便宜很多。

这一层读完，动手做一件事

挑一个你手上得分好几次才能做完的任务，照着长任务那篇的办法完整做一遍。

先让 Agent 建一份任务清单和一个进度文件，每次只做清单上的一项，做完就更新进度、提交一次。第二天开一个全新的对话，只告诉它一句“读进度文件，继续”，看看它能不能无缝接上。

如果能接上，你就真正理解 Harness 在干什么了。
