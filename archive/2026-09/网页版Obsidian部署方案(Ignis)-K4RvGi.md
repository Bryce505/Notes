先看效果

现在我在任何一台设备的浏览器里输入一个地址，输入一次账号密码，看到的就是我完整的 Obsidian：编辑器、白板、关系图、主题、快捷键都在，手机浏览器打开还有移动端界面。公司电脑、iPad、别人的笔记本，不用装任何客户端。

[图片]

更关键的是，浏览器里写的每一个字，十分钟内自动提交进 git 仓库，桌面端的 Obsidian 拉一下就是最新的。笔记永远只有一份，都在 git 仓库里。

这篇文章讲我怎么把这套东西在自家 NAS 上搭起来的：先看整体结构，再说为什么是 Ignis，最后是四个踩坑记录。

要解决的问题

需求一句话：一个网址，输完密码就是我的笔记库，改完就走，数据自动回 git——不装客户端，任何设备的浏览器都行。

为什么会有这个需求：我的笔记库是个 git 仓库，放在自家 NAS 的 Gitea 上，桌面 Obsidian 直接对着它工作，这个结构在家很稳，但有个问题始终没解决：出了门怎么办。官方 Sync 是订阅制且数据在别人服务器上，不符合我的自托管路线；Syncthing、Remotely Save 这类方案本质是文件同步，手机上还是得装 Obsidian 客户端加一堆配置；至于在别人电脑上临时查篇笔记，这些方案全都无解。

整体方案

方案一句话： Ignis 容器负责网页入口，NAS 上 clone 一份 git 工作树、用 bind mount 把笔记目录挂进 vault，宿主机 cron 每 10 分钟把改动提交回仓库。 为什么选 Ignis，下一节交代；这一节先看清整体结构：

[图片]

git 仓库是唯一事实源。浏览器和桌面客户端都只是它的两个窗口，任何一端的改动最后都进同一个仓库。

照着架构图从下往上，分三层看。

Ignis 容器层。 就是官方镜像跑起来的服务，负责在浏览器里呈现 Obsidian。性能上有两个数字让我放心：官方专门为大 vault 做了预压缩启动响应和 LRU 内容缓存，缓存默认 50MB，不会把整个库都加载进内存。

vault 组装层，这是我自己加的部分。 我的 git 仓库里不只有笔记，还有一堆工程文件，全部暴露给 Obsidian 既慢又乱。所以我做了一个 装配式 vault ：vault 本体只是个空目录，里面用 bind mount 把仓库里的笔记目录（wiki、文章、书摘这几个）逐个挂进来。有一个坑值得一提：一开始我用的是软链接，结果桌面端走 SMB 访问时软链全是断的——SMB 协议不跟随服务端的软链接。换成内核级的 bind mount 之后，SMB、Ignis、本地访问看到的都是真实目录，三端表现一致。

自动同步层。 Ignis 容器出于安全设计禁用了子进程，所以 Obsidian 的 git 类插件在容器里跑不了，同步必须放在宿主机做。我用一个十来行的 shell 脚本加 cron 实现定时器：每 10 分钟对工作树做一次 pull --rebase（带上 autostash，保护未提交的编辑），有改动就 commit 并 push 回 Gitea。整套东西我写成了 Ansible role，clone、挂载、fstab 持久化、定时任务一条命令全量部署，换台 NAS 也能复现。

选型过程

先说结论：试过的方案按失败原因分三类—— 只读 （Quartz 静态发布）、 体验不行 （VNC 投屏）、 没解决无客户端访问 （文件同步类）。缺的是一个 原生 方案：不装客户端、不是静态快照、不是投屏，就是 Obsidian 直接跑在浏览器里。Ignis 补上了这个缺口。

第一类，只读：Quartz 静态发布。 Quartz（github.com/jackyzha0/quartz）把 vault 编译成一个网站，双向链接、关系图、全文搜索都有。但它本质是 发布 ，不是 使用 ——只读，改一个字要重新构建，白板和 Bases 这些功能渲染不出来，私人笔记也不适合全量公开。拿它对外分享可以，当自己的日常编辑器不行。

第二类，体验不行：VNC 远程桌面。 NAS 上开一个跑着 Obsidian 的桌面环境，浏览器里连过去操作。操作的对象确实是真 Obsidian，但 VNC 传输的是整屏画面，延迟高、画质糊，手机上几乎没法点击，网络一波动整个画面就卡住。用了一阵子，结论是这条路不适合日常记笔记。

第三类，没解决无客户端访问：文件同步类。 Syncthing、Remotely Save、基于 CouchDB 的 LiveSync，它们解决的是 多设备文件一致 ，手机上还得装客户端，别人电脑上临时查篇笔记照样无解。

Ignis 补上缺口。 它把真正的 Obsidian 跑在 Docker 容器里，通过服务端转发，把整个界面渲染到浏览器上（github.com/Nystik-gh/ignis）。注意这不是 仿一个 Obsidian 网页版 ，就是 Obsidian 本身在跑——编辑器、白板、Bases、主题、大部分社区插件都可用，多标签页之间还能通过 WebSocket 实时同步。项目 AGPL 开源，一千二百多 star，作者把它当自己的日常笔记工具在维护，更新很勤。

[图片]

定位也要说清：Ignis 不适合面向大众的公开分享——它是个带认证的私有入口。所以现在两个方案并存：要公开的内容还是 Quartz 编译出去，私人库和小团队共享走 Ignis。一个管 公开分享 ，一个管 自用 ，不冲突。

值得说一句的官方背景：项目明确声明与 Obsidian 官方（Dynalist Inc.）无隶属关系，容器在运行时从 Obsidian 官方源下载程序本体，仓库里不含任何 Obsidian 的代码和资源，依据的是欧盟软件指令的互操作条款。部署本身很简单，官方 README 的快速开始给了一个最小示例：一条 docker compose 配置，映射 8080 端口，把宿主机的 vaults 目录挂进容器， docker compose up -d 之后打开 localhost:8080 就能用了。我的整套方案就是在这个官方示例之上，加了 HTTPS 反代、密码认证，以及前面讲的 git 工作树结构。

官方有个重要提醒必须照做：Ignis 本身没有内置认证，任何人到达你的实例就能读写整个 vault，所以暴露到公网前一定要套 HTTPS 和认证。我的做法是 nginx 反代加 Basic Auth，打开时先过一道账号密码。

踩坑记录

四个坑，按发现难度排序：一个性能问题，两个不报错的静默失败，一个重启后才出现的状态问题。每个都花了不少时间定位。

大 vault 拖垮启动。 最初把整个工作区当 vault，Ignis 启动要 16.5 秒，因为里面有 11 万多个非笔记文件。把工程数据隔离出去之后，文件数降到四千多，启动 0.6 秒。这就是做装配式 vault 的直接原因。

删除静默失败。 有一阵在网页里删文件毫无反应，也不报错。最后定位到两层原因：其一，容器里没有系统回收站，而 Obsidian 默认删除是 移入系统回收站 ，删除动作直接没生效，把 vault 配置改成软件内回收站（.trash 目录）就好了；其二，也更隐蔽——我的 vault 子目录是 bind mount，删除文件本质是一次跨挂载点的 rename，Linux 内核对这种操作直接拒绝（EXDEV 错误），服务端返回 500。我给服务端的文件接口打了个兜底补丁：跨挂载点时自动降级为复制加删除。这个问题应该任何用 NFS 或子目录挂载的用户都会撞上，值得提给作者。

Bases 打不开。 新建的 .base 文件双击没反应。原因是 vault 配置里 Bases 核心插件默认是关的，开启之后刷新页面就好。这种 不报错的失败 最难排查。

重启后的旧标签页异常。 服务重启后，一直开着的旧标签页会处于异常状态：还能编辑，但删除和重命名没有反应。重新加载页面即可恢复。

效果与遗留问题

结论先行：方案跑稳之后，日常维护成本约等于零，但有三件事要知道——索引窗口期、同时编辑的冲突可能、容器重建后补丁要重打。

现在的日常：出门用手机浏览器写两笔，回家桌面端拉一下就是最新的；在别人电脑上要查资料，开个浏览器标签就行。整个方案 Ansible 化之后，维护成本约等于零。

遗留问题也交代一下。大 vault 打开后头几十秒，索引还在后台慢慢建，这个窗口期里删除类操作可能没反应，等一下再试就好（这是 Obsidian 索引机制决定的，Ignis 侧没法完全消除）。10 分钟的同步窗口意味着，如果我在浏览器和桌面端 同时 编辑同一个文件，理论上会产生冲突，脚本对此的处理是跳过本轮并记日志，不强行合并。另外那个 EXDEV 补丁打在容器里，重建容器后要重打——我的 Ansible role 已经把重打做成自动的，但升级镜像后第一次部署多花几秒而已。
