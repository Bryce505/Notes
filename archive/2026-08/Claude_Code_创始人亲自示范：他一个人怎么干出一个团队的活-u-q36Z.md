你有没有过这种感觉：明明用的是同一个 AI 工具，别人用起来像开了挂，自己用起来却跟普通聊天没什么两样？

这篇文章要讲的人叫 Boris Cherny。他是 Claude Code 的创始人和团队负责人——Claude Code 是 Anthropic 出品的一款 AI 编程工具，开发者可以在终端（就是程序员用的那个黑底白字的命令行窗口）里直接让 AI 帮忙写代码、改 bug、跑测试。

Boris 用自己做出来的这款产品的方式，跟大多数人完全不一样。

所有人都在研究怎么写更好的 prompt（提示词，你输入给 AI 的指令）。Boris 干脆放弃了这个思路。他没有特殊模型，没有奇怪的配置——他说开箱就很好用，几乎不做定制。 秘诀不在工具本身，而在他怎么把整天的工作节奏围绕它来设计。

最让人想不通的是：他的个人配置简单到近乎无聊。五个终端标签页，一个文本文件，几条快捷命令，一条他反复强调的原则。就这些，拼在一起，让一个工程师具备了一个团队的产出。

以下是他的实际方法，来源：他本人 1 月份发的工作流分享帖、Lenny Podcast 和 Pragmatic Engineer 的深度采访，以及 Fortune 的报道。不是理论，是他每天在做的事。

第一部分：他在指挥乐队，不是在跟聊天框说话

五个本地会话，十个网页会话，还有一个是早上躺在床上用手机启动的。

大多数人用 AI 编程是这样的：开一个对话窗口，输入一段指令，等 AI 回复，看看代码对不对，再输入下一段。整个过程就像跟一个人聊微信——你说一句，它说一句，一来一回。

Boris 不是这么用的。他同时跑一群 Claude。

五个 Claude Code 会话开在 MacBook 的终端里，标签页编号 1 到 5，系统通知告诉他哪个需要他介入。与此同时，还有 5 到 10 个会话跑在网页版 claude.ai/code 上。也就是说，他同时有 10 到 15 个 AI 在帮他干活。

这些会话之间还能互相转移。他用 --teleport 命令把网页端的会话拉回本地终端继续做，反过来也行。早上还没坐到工位，就在手机上的 Claude 应用里启动了当天第一个任务。

一个很多人搞错的细节 ：他的每个本地会话用的是完全独立的代码副本（git checkout），不是在同一套代码上开不同分支。这意味着什么？五个 AI 同时改同一个项目的不同部分，完全不会互相冲突——就像五个厨师各自有一个独立的厨房，做完了再把菜端到一起。

"I don't prompt Claude anymore. I have loops that are running. They're the ones that are prompting Claude and figuring out what to do. My job is to write loops."  "我不再给 Claude 写提示词了。我有循环在跑，是它们在给 Claude 写提示词、决定下一步做什么。我的工作是写循环。"  ——Boris Cherny

[图片]

他也坦率地说了混乱的部分： 10% 到 20% 的会话会半路废掉 ，因为碰到了意料之外的情况。没关系——你同时跑二十个，扔掉三个不算什么。这跟传统的"一个任务一个人从头跟到尾"的方式完全不同。他把失败的成本摊薄了。

他也不挑模型。所有任务都用 Opus 思考模式（Claude 最强的推理模式，推理更慢但更准）。有人可能会问：更慢不是更浪费时间吗？不是。因为你更少需要纠正它，它调用工具更准，整个任务做下来反而更快。而且当你同时编排十几个会话时，单个会话快不快已经不重要了—— 反正等的人不是你，你在忙着处理其他会话。

瓶颈不再是写代码，而是在写代码的那群 AI 之间切换注意力。

这句话值得停下来想一想。以前程序员的瓶颈是"写代码太慢"。现在 Boris 的瓶颈变成了"AI 写得太快，我来不及看"。同一份工作的难点，完全转移了。

第二部分：复合工程——那个会自己学习的文本文件

每次犯错变成一条规则。规则共享给所有人。团队每周都在变聪明。

Boris 的记忆系统说出来你可能不信：就是一个纯文本文件，叫 CLAUDE.md，跟代码一起存在项目仓库里。

不是什么高级的向量数据库，不是花大钱做的模型微调，就是一个普普通通的文本文件。但它的特别之处在于： 每次 Claude 会话启动时，都会先读这个文件。 文件里写什么，Claude 就按什么来。

这个文件是整个团队共有的。Boris 的团队每周往同一个 CLAUDE.md 里写好几次。规则很简单： 任何时候 Claude 做错了什么——比如用了不该用的代码风格，漏掉了某个检查步骤——纠正就立刻写进去，下次它就不会再犯。

文件里存着什么？代码风格规范、设计指南、PR（Pull Request，代码合并请求，就是程序员把自己写的代码提交给团队审核的流程）模板，还有那些血泪教训："千万别这么干，上次这么干出了大事故"。

"Anytime Claude does something incorrectly, we add it to the CLAUDE.md so it knows not to do it next time."  "每次 Claude 做错了什么，我们就把纠正写进 CLAUDE.md，这样它下次就知道不该那么做了。"  ——Boris Cherny

[图片]

Boris 个人的 CLAUDE.md 呢？基本就两行，指向团队共享的那一份。团队文件大约 2500 个 token（token 是模型处理文字的计量单位，越多越贵）——刻意保持精简，因为他很清楚一份臃肿的指令文件有多烧钱（后面会讲）。

最精妙的一招在代码审查环节。 Boris 审查队友的代码时如果发现了反模式（就是那种"能跑但不该这么写"的做法），他不只是留个评论。他在这条代码审查记录上 @Claude（通过 GitHub 的自动化流程），让 Claude 把这条教训直接写进 CLAUDE.md，作为同一次提交的一部分。 修复和规则一起合并进代码库。

这就是他说的"复合工程"（compound engineering）。什么意思？代码库本身随着每次合并变得更聪明。就像往银行存钱：每一条写进 CLAUDE.md 的规则都是存进去的本金，之后每次 AI 运行都能吃到利息。一个月前团队踩过的坑，一个月后新来的人不会再踩，因为 AI 已经知道了。这种知识积累是自动的、持续的，不依赖任何人的记忆力。

第三部分：先做计划，然后让开

一次完成是个谎言。计划才是真正的工作。

你有没有过这种经历：让 AI 帮你写一个功能，结果它一口气写了一大堆代码，但做出来的东西完全不是你想要的？

大多数人遇到这种情况会怪模型。Boris 怪的不是模型， 是缺少计划。

他的默认操作是 Plan 模式（在 Claude Code 里按两次 Shift+Tab 就能切换）。这个模式下，Claude 不会写任何代码，只会跟你讨论方案。Boris 会跟 Claude 在计划上反复讨论——"这部分应该怎么拆？""这里你打算用什么方式实现？""不对，我想要的是这样的"——直到计划跟他脑子里想的完全一致。

然后才切换到自动接受修改模式，让 Claude 放手去跑。

"If my goal is to write a Pull Request, I will use Plan mode, and go back and forth with Claude until I like its plan. From there, I switch into auto-accept edits mode and Claude can usually 1-shot it. A good plan is really important!"  "如果我的目标是写一个 PR，我会用 Plan 模式，跟 Claude 反复讨论直到我满意它的计划。然后切换到自动接受修改模式，Claude 通常能一次完成。一个好计划真的非常重要！"  ——Boris Cherny

[图片]

为什么大多数人"让 AI 一次写完"总是失败？ 原因是信息带宽不够。 你用寥寥几个词描述了一个复杂功能，AI 理解到的只是你脑海中画面的一个模糊轮廓，做出来的自然是另一个东西。

做计划就是在写第一行代码之前，把你脑子里的细节一点一点传递给 AI，把双方的理解对齐。等计划对齐了，AI 一次写完的成功率就大幅提高。所谓"神奇的一次完成"，不是 AI 有多聪明，只不过是一个好计划在兑现。

类比一下： 这就像装修房子。你跟装修师傅说"帮我弄个现代风格的客厅"，他做出来大概率不是你想要的。但如果你先花两小时跟他对着效果图一项一项确认——地板材质、灯的位置、沙发颜色、电视墙要不要——然后让他去做，结果就完全不同了。AI 编程同理，计划就是那两小时的对图。

第四部分：内循环，变成了代码

任何做了两次以上的事，都变成一条命令、一个子智能体或一个钩子。

这是 Boris"普通配置"悄悄变成机器的地方。他不会为常规工作重复输入 prompt——他把重复的操作编码了，让它自动执行。

具体怎么做？四个层面：

第一层：斜杠命令（slash command）。 在 Claude Code 里，你可以用 / 开头的快捷指令来触发预设的操作，就像微信里的快捷回复。Boris 把每个日常操作都做成了斜杠命令，存在 .claude/commands/ 文件夹里，团队里的人和 Claude 自己都能用。

他用得最多的一条叫 /commit-push-pr ——写完代码后一键提交、推送、开合并请求。他每天跑几十次。这条命令的巧妙之处在于：它会先用 bash 脚本算好当前代码的状态，这样 AI 不用浪费一轮对话去搞清楚"现在改了哪些文件"，直接干活。

第二层：子智能体。 你可以理解为 AI 的下属——主 AI 把一部分工作派给"下属 AI"去做，做完了只拿结果，不把过程中的杂乱信息带回来。Boris 常用两个子智能体：一个叫 Code Simplifier，在 Claude 写完代码后自动做简化清理（就像编辑帮作者删掉多余的废话）；一个叫 Verify App，带着详细指令做端到端测试（从用户的角度完整走一遍功能流程，看有没有问题）。

第三层：钩子（hook）。 钩子是一种"自动触发"机制——设定好之后，每次某件事发生，它就自动执行一个动作。Boris 设了一个 PostToolUse hook，意思是"每次 AI 调用完一个工具之后，自动跑一次代码格式化"。Claude 的代码本身已经挺干净，这个钩子负责最后 10% 的格式统一，省得后面 CI（持续集成，代码提交后自动跑测试和构建的流水线）被格式问题绊住。

第四层：MCP 连接外部工具。 MCP（Model Context Protocol，模型上下文协议）是一种让 AI 调用外部工具的标准接口。通过 MCP，Boris 的 Claude 可以直接发 Slack 消息通知团队、用 BigQuery（Google 的大数据分析工具）查询业务数据、从 Sentry（错误监控工具）拉取线上报警。这些连接全部存在代码仓库里，团队共享。

他的警告：MCP 虽然强大，但每多接一个工具，AI 的上下文窗口（它一次能"记住"的信息量）就会膨胀一点，而且外部工具的描述可能被人恶意篡改来操纵 AI。所以安装任何 MCP 之前，先让 Claude 审查一遍它的代码。

至于权限管理 ，他几乎从不用 --dangerously-skip-permissions （跳过所有安全检查的危险模式）。而是用白名单方式，把安全的命令（ bun run build 、 bun run test 之类）列进 .claude/settings.json ，跟团队共享。所有人一次性约定好"哪些操作 AI 可以自动做，哪些必须问人"。

[图片]

Boris 的经验法则：每次做一件事，就顺手造一个下次能替你做这件事的东西。意图会复合增长，prompt 不会。

这句话的意思是：你今天花十分钟把一个重复操作做成了自动命令，明天、后天、大后天它都在替你省时间。但如果你每次都手动输入 prompt，今天的投入明天归零，永远在从头来。

第五部分：验证才是整个游戏

他最重要的一条建议，跟写 prompt 没有任何关系。

如果你只从 Boris 的工作方式里带走一样东西，带走这个： 给 AI 一种检查自己工作的方式，它会反复打磨直到真正做好。

什么意思？大多数人让 AI 写完代码就直接看结果了。Boris 不是这样——他给 AI 配了一整套"自我检查系统"：写完代码后，AI 自己跑测试、自己检查类型、自己编译构建，甚至自己打开浏览器看界面效果。如果哪一步没通过，它会自动修改代码再试，直到全部通过为止。

"Claude tests every single change I land to claude.ai/code using the Claude Chrome extension. It opens a browser, tests the UI, and iterates until the code works and the UX feels good."  "我提交到 claude.ai/code 的每一个改动，Claude 都会用 Chrome 扩展自己测试。它会打开浏览器，测试界面，反复迭代，直到代码跑通、用户体验也顺畅。"  ——Boris Cherny

[图片]

一个真正的反馈循环（测试套件、类型检查、构建、浏览器、模拟器）能让最终结果好 2 到 3 倍。没有反馈循环会怎样？AI 写完代码，自己看一眼觉得"不错"，交给你。这就像学生自己给自己判卷，每次都给满分——问题是它根本不知道自己错在哪。

对于长时间运行的任务，Boris 会分层验证：让一个后台 AI 在主 AI 完成后检查结果（相当于找另一个人复核）；用钩子做确定性的通过/不通过判断（不靠 AI 的主观判断，靠客观的测试结果）；或者跑一个自主循环插件，完全不需要人盯着。

每个层级的道理都一样—— 循环只在现实说"过了"的时候才往前走，不是 AI 自己说"我觉得行"就行。

效果体现在团队怎么分配时间。因为验证跑在 AI 的循环内部，人类被解放出来做机器还做不了的两件事： 审查和把方向。 等工程师打开代码审查页面的时候，代码已经经过了多轮自动测试，处于良好状态了。人类的时间从"逐行检查代码有没有 bug"转移到了"这个方案的方向对不对"。

第六部分：Tokenmaxxing——多花 token，但别花冤枉钱

多花，但不是乱花。

Boris 给公司的建议听起来像是冒险，直到你听到后半句。

"Don't try to cost cut at the beginning. Give engineers as many tokens as possible."  "一开始别急着省钱。给工程师尽可能多的 token。"  ——Boris Cherny

[图片]

他管这叫 tokenmaxxing——把 token 花到极致。token 是 AI 模型处理信息的计量单位，你每跟 AI 对话一轮，输入和输出都在消耗 token，消耗越多费用越高。

Boris 的观点是： 真正的瓶颈从来不是 token 的成本，而是工程师学会善用 AI 的速度。 限制用量就是掐住了学习。一个工程师刚开始用 AI 编程时，效率可能还不如自己手写。但随着他摸索出窍门（什么时候该用 Plan 模式、什么任务适合并行、怎么写 CLAUDE.md），效率会越来越高。你在这个阶段限制 token，等于不让新手练车就指望他上路。

而且你拿 Claude Code 比的对象不应该是 20 美元一个月的编程助手。应该比的是雇一个工程师做同样工作的人力成本。一个工程师的年薪可能是几十万，每月 AI 工具费用可能只有几千块。按这个基准看，token 花得值不值就一目了然了。

但"多花"不等于"乱花"。 Boris 在一次播客中详细讲了 token 是怎么被无谓消耗的——一大块浪费在臃肿的 CLAUDE.md 上（AI 每次启动都要读这个文件，文件越大，消耗的 token 越多），另一大块浪费在重读旧的对话历史上。

这恰恰是为什么他团队的 CLAUDE.md 精简到只有 2500 个 token，他个人的只有两行。 该花的钱往死里花（多开会话、多跑验证、多做并行），不该花的钱一个 token 不浪费（精简配置文件、减少无效上下文）。

第七部分：诚实的部分

这套方法没法解决的事。

如果这篇文章到第六部分就结束了，它会是一篇标准的吹捧稿。但原文作者很诚实，Boris 本人也很诚实。所以有第七部分。

这一切不是取消了工程师，而是把工程师挪了个位置。

问题一：废弃率。 Boris 有 10% 到 20% 的 AI 会话中途废弃。同时跑二十个会话，扔掉三四个"不算什么"，但这意味着有真实的资源浪费。

问题二：审查瓶颈转移。 以前的瓶颈是写代码太慢。现在 AI 代码写得飞快，瓶颈变成了人类来不及看代码。代码审查成了新的瓶颈——AI 帮你干活干得越快，你需要审查的东西就越多。

问题三：理解力的黑洞。 这是最深层的风险。一群 AI 飞速产出没人手写过的代码，代码仓库里"有但没人读过"的部分就越来越大。工作流越顺滑，这个缺口就越滚越大。总有一天你得调试一个没人读过的系统——那天的成本比所有 token 加起来都大。

两个工程师用同样的方法，可以得到完全相反的结果。一个用它加速自己深度理解的工作，另一个用它来彻底放弃理解。 工具分不出这两种人，但你自己分得出。

[图片]

Boris 不再手写代码了。他不再逐轮输入 prompt 了。但他没有停止做计划、做审查、把方向——这些才是真正属于他的部分。

这就是他的方法。不是更好的 prompt，而是一个更好的位置： 从打字的人，变成做判断的人。
