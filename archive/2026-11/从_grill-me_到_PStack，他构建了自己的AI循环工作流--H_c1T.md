从 /grill-me 到 PStack，他构建了自己的AI循环工作流

距离 Damian Galarza 写下《Claude Code 工作流：我的完整开发环境配置》已经快 12 个月。这期间 Opus 4.5 成了智能体工作流真正的转折点，Fable 5 上线时一度暂停服务，回来之后又把上限抬高了一截，OpenAI 随后放出 GPT-5.6 系列的 Luna、Terra 和 Sol。他的工作流跟着变了很多。

[图片]

Damian Galarza 做 AI 原生工程咨询，帮团队把智能体编程落到生产里。一年前他的流程只围绕一个工具，现在围着三个转，中间还有一个终端工具把它们拢在一起。他把这一年的变化写成了一篇长文，下面是他现在的做法。

一年前只有一个工具，现在有三个

最初那篇文章里他说过一句话，上下文为王。这句今天仍然成立，也是他一直盯着上下文窗口不放的原因。

2026 年 5 月，他的 Claude Code Max 套餐撞上了周额度上限。这件事推着他去认真试了 Codex。

试下来的结论很直接，那是一个出色的编程运行框架，当时他觉得比 Claude Code 更好。桌面端和移动端让他从手机上接手工作这件事比 Claude Code 的远程控制和派发自然得多。GPT-5.6 出来之后，Sol 比 Opus 4.6 高效。再加上内置浏览器和原生的多智能体委派，整个生态给他的感觉是上了一个台阶。把智能体派到工作树里的新线程上，顺手得不像话。

Pi 是另一条路。它是一个极简的开源智能体运行框架，理念是“原语，而非功能”，有意砍掉了子智能体、计划模式和权限提示，让用户通过扩展和包自己加回来。

它能接的模型和供应商范围很宽。Damian 最早是在 August Health 用它，当作连接公司 Amazon Bedrock 模型的简便方式，等开始用 herdr 在终端里管编程智能体之后才算真正用上。Codex 至今有一个 bug，启动或管理 herdr 面板和智能体并不可靠，Pi 正好补了这个空缺。

Claude Code 一直留在他的组合里。OpenAI 的模型进步了多少是另一回事，他认为 Anthropic 在几个领域仍有优势，尤其是设计。Claude Design 用起来格外好，Fable 和 Opus 在构建前端体验上明显更强。GPT-6 Astra 和 GPT-6 Sol 发布后差距缩小了一些，但按他的经验，Claude 的 artifacts 和设计系统仍然是最出色的。

回到 Claude Code 还有工具层面的原因。他的多智能体工具做得相当好，尤其是 ultracode。

在提示词里带上 ultracode ，或者用 /effort ultracode 对整个会话开启，Claude 会把计划写成一个工作流脚本，然后在后台把工作分发到一个智能体团队上，而会话本身仍然保持响应。 /advisor 会给主模型配一个更强的模型，让 Claude 在关键节点咨询它，比如在确定某个方案之前，或者在宣布任务完成之前。连内置插件也额外调用智能体，You Should Know 会在长会话旁边跑一个，标记 Claude 或人可能漏掉的东西。

三个生态怎么拢在一个面板里

herdr 是他最喜欢的几个新工具之一，一个专为智能体构建的终端复用器。它最讨喜的地方是跨类型协调智能体毫不费力。常见的组合是 Claude Code 里的 Opus 5.5 智能体做编排，把零碎的部分交给 Pi 或 Codex 里的智能体。多数时候接活的是 Pi 里一个跑在他 DGX Spark 上的 qwen3.8-flash-next 智能体，这样相当一部分工作就卸载到了本地模型上。

能做到这一点，是因为 herdr 把控制权也给了智能体。装好它的 agent skill 之后，一个智能体可以通过 herdr 的命令行建工作树、在工作树里启动另一个智能体、给那个智能体发提示词。每个智能体都显示在一个面板里，带着当前状态，是在工作、被阻塞还是空闲，需要人来处理时会收到通知。herdr 以后台服务的形式运行，关掉终端不丢东西。通过 SSH 也能连上去，Damian 经常在手机上这么干。

DHH 最近把这件事讲得很到位。

[图片]

他的版本是一台放在桌上、关掉睡眠、接在 Tailscale 网络里的 MacBook Pro。离开桌子的时候，他用手机上的 Termius 连回去，接着用留下的那些会话。手机是 Galaxy Z Fold 8，旁边还有一台跑本地模型的 DGX Spark。照他自己的说法，离 DHH 讲的“豪华棚屋”已经走了大半。

上下文从哪来

Damian 把上下文列为排查智能体出错时要检查的四个杠杆之一。第一来源是代码库本身。

Lauren Tan（X 上叫 poteto）在一场讲“一个月发出 2500 个 PR”的分享里说，代码库是智能体手里最可靠的一份记忆，因为智能体会扩展它眼前已经存在的模式。代码里满是绕过去的权宜做法，智能体就照抄。她的建议是把每一次纠正尽量往代码那边推。先用架构让这类错误不可能发生，其次用静态分析抓住它，最后才退回到规则和技能。

如果拿不准自己的代码库处在什么水平，Codebase Readiness 会给仓库的智能体就绪度打分并排出优先级路线图，Agent Ready 会搭出智能体理解代码库所需的文档。

[图片]

代码库之外还有大量信息散在工单、生产错误、会议记录和文档里，他给每一类都接了入口。

Linear 是他组织软件项目的主要工具。通过 Linear MCP 连上之后，只要在做某个 issue，把 issue ID 交给智能体，它会自己去收集需要的上下文。他下给智能体的指令通常只有一句，比如 ❯ Implement PRX-66 。反方向同样有效，智能体把进度写回 Linear，下一个智能体就能接手，明白做到哪一步、接下来怎么走。

Sentry 命令行用来排查生产问题。智能体可以把 Sentry 里关于某个问题的所有东西拉下来，包括堆栈，配上环境里的日志，对故障的成因就掌握得很清楚。

能选命令行的时候他选命令行，理由很朴素，轻，而且在每个智能体上表现一致。Sentry 也提供 MCP，Datadog 有官方 MCP 服务器覆盖 APM、日志和监控。

会议记录是第三块。他用的工具是 Fireflies，因为喜欢录音和笔记放在一起，过去也用过更轻的 Granola。两个都有官方 MCP 服务器。开会时他仍然手写笔记，写下来帮他记住，但录音真正划算的地方是接给智能体之后，去做那个 issue 时可以把智能体指向相关的通话，把当时讨论的完整上下文收齐。

最后是 Notion 和 Obsidian。Notion 是公司的第二大脑，团队之间在那里共享知识，通过 Notion MCP 接。团队如果用 Confluence，Atlassian 的 MCP 服务器覆盖了它。Obsidian 存在本地，所以他在全局指令文件里加一行，告诉智能体库在哪里。每个智能体的位置不一样：

： ~/.codex/AGENTS.md

： ~/.claude/CLAUDE.md

： ~/.pi/agent/AGENTS.md

有些智能体还支持 ~/.agents/AGENTS.md 。每个文件里一行就够。

循环只有四段

上下文就位之后，工作这么流转。他把流程看成一个四段循环，每一段有自己的一组技能。

[图片]

塑形，把工作整理成定义清晰的 issue。构建，用智能体逐个实现。评审，检查智能体产出的东西。发布，然后绕回去，塑形下一个问题。绕一圈就是处理完一件工作，从塑形成 issue 到把它们发出去。

塑形：先让问题值得交给智能体

如今他相当一部分精力花在塑形上，也就是确保工作已经准备好让智能体接手。这从扎实理解要解决什么问题开始，然后是一份站得住的规格，再把工作拆成智能体能迭代推进的片。

塑形和计划模式不是一回事。计划模式帮智能体想清楚怎么实现一个方案，塑形是为了在任何人谈“怎么做”之前，先确保问题被理解了。工作塑形得好，他几乎就不再动用计划模式。

他的塑形技能来自 Matt Pocock，四个技能覆盖从问题到代码的整个过程：

就一个计划或设计无情地访谈，适合非编程问题。

跑同一套访谈，但边走边写文档，把决策记成 ADR，把术语记进词汇表，所以更适合编程工作。

构建并磨利项目的领域模型，也就是代码背后的词汇和决策。

给智能体一套共享词汇，用来设计深层模块，干净的接口、位置合适的接缝、容易测试的代码。

两个拷问类技能都建立在父技能 grilling 之上， grill-with-docs 还会拉进 domain-modeling 。用 npx skills add mattpocock/skills 全部装上，他是全局安装的，所有项目都能用。

这些技能保证在写下第一行代码之前，人和智能体对要做的东西已经达成一致。拷问的过程是一串问题，决策在过程中一个个定下来。用 grill-with-docs 时，那些决策和术语会被写下来，未来的智能体也能拿到这份上下文。README 的原话是，就一个计划或设计被无情访谈，直到设计树的每个分支都被解决。

下面是他为 Praxis 塑形 artifacts 功能时的一次拷问节选（原文为英文，此处为中译）：

第 1 轮，这些是根决策，其余一切都挂在上面。

问：v1 里谁能看 artifacts？是只给你自己，通过 Tailscale 上的私有管理后台看，客户侧分享推迟到后面一个阶段？另一种做法是一开始就做分享链接和公网入口，那会把 Cloudflare 仓库和一个 token 模型在第一天就拉进来。

答：对。只有你，管理后台，Tailscale。客户分享是后面的阶段。

问：词汇。现在就把这些词定死？Artifact 是一个带标题、类型、范围和标签的稳定身份。Version 是 artifact 文件的一次不可变发布快照。Head 是当前版本。你今天用这些词的方式有不同吗，尤其是 project 这个词？

答：对，“project”到处都是指合作项目，没有单独的项目概念。

拷问结束，他把共识变成一份规格和一组 issue。这一步用两个内部技能， spec-writer 和 issue-writer ，受了 Matt 的 to-spec 和 to-tickets 启发。

spec-writer 把拷问已经定下来的东西综合成一份短规格，不再重新访谈一遍，内容包括问题、方案、带编号的规则、决策、开放问题、怎么测、什么不在范围内，然后通过同一条 Linear MCP 连接存成 Linear 文档，放在正确的项目里。

issue-writer 把规格拆成小的纵向切片，切片之间有阻塞关系。每张工单写清楚要做什么、怎么算做完、不要碰什么，并且以 ID 的形式链接回规格里的规则，而不是复制过来，这样每条规则只活在一个地方。

一份真实规格里的规则长这样：

R1，只重试可识别的临时供应商故障，包括过载、临时速率限制、可重试的服务端响应和网络中断。

R2，永久性和含糊的故障保持终态，认证失败、配额耗尽、无效响应、取消和未分类错误从不自动重试。

R3，有界指数退避，在 30 秒、2 分钟和 8 分钟后重试，抖动正负 20%。自动重试三次，总共四次尝试。

R4，保持一个逻辑任务。重试沿用同一个任务 ID 和同一个目标提交。重复的 webhook 投递既不新建任务，也不重置重试预算。

规格的其余部分同样具体。问题段落说清楚临时故障为什么会让一次评审永久失败，方案段落定下有界指数退避配上界面上的“Retry scheduled”提示和下次尝试时间。测试段落给出一条集成流程，从过载到持久化的重试，到工作进程重启，再到一次成功的新尝试，最后恰好发布一份评审。范围外一栏明确排除手动重试开关和供应商回退。

构建：把实现交给一套技能

工作塑形完，实现通常交给一个全新的智能体，而不是在塑形的会话里继续做，这样实现是从一个干净的上下文窗口开始的。用 herdr 建一个新工作树，然后按工作性质挑智能体。简单、一次性的工作用 Codex，想委派或铺开的多步工作用 Pi，前端和视觉工作或者需要智能体去编排的复杂工作用 Claude Code。

不管挑哪个，构建都跑 pstack。那是 Lauren Tan 做的一套工程技能。她的描述是无惧的并行，当你能在一个智能体上深挖，并且信任它写出好的、可验证的代码时，你就能真正有底气地并行。

Damian 对大型技能包一向持怀疑态度，理由是它们加进来的流程比带来的价值多。pstack 是例外。它在 Cursor 的 plugins 仓库里开源，优先为 Cursor 做，也能从同一个市场装进 Claude Code。还有面向其他编程智能体的移植版，比如 Michael Denyer 的 pstack-claude，跟着 Lauren 的改动走，覆盖 Claude Code、Codex、Pi 和另外几个框架。因为一天里会在三个工具之间移动，他用的是这个移植版。

不管装哪个版本，pstack 的组织方式一样，分三层。

/poteto-mode 是入口。用它起一个任务，描述想要什么，它把任务匹配到 23 个执行手册中的一个，比如修 bug、功能、重构、原型、性能、发布，然后在开始之前先把那份手册的步骤抄进一个待办清单。修 bug 的手册要求智能体先复现缺陷、找到根因，然后才碰修复。对大多数任务来说，只需要这一条命令。

情境技能在它下面。 /how 走一遍某个子系统是怎么工作的。 /why 翻 git 历史、PR 评论和 issue 跟踪器，解释当初为什么那么建。 /architect 在实现开始前先把类型和调用点定下来， /interrogate 让不同模型试着打破一个改动。执行手册的某个步骤需要的时候， /poteto-mode 会自己调用其中大部分技能，只在特别想要某一个时才直接伸手。

原则把这一切拴在一起。pstack 带了 24 个简短的原则技能，一条原则一个，分成核心、架构、验证、委派和元几组，每个任务开始时 /poteto-mode 会读一遍它们的索引。

[图片]

其中六条能体现它的精神：

：倾向于删除，倾向于解决问题所需的最小改动。

：先删掉死代码和多余的检查，再在更简单的基础上构建。

：去造那个把活干完的 codemod、脚本或生成器，而不是手工做，这样评审者可以重跑。

：把症状追到系统第一次出错的那个点，在那里修。

：对着真实的东西验证，运行功能、读实际的数值，而不是“它编译过了”或者智能体自己的汇报。

：做那个可回退的决定，继续走，让人事后纠偏。

[图片]

pstack 有意不带计划技能。README 说得直白，就他个人而言，他不相信计划，认为规格本身就是代码。设计问题用一次性的原型和 /architect 的草图解决，而不是写很长的抽象计划。这跟塑形配合得上，塑形定下做什么和为什么做，pstack 在代码里把“怎么做”算出来。

验证是这一切的地基。Lauren 那套《pstack 完全指南》的第一篇标题就是“验证就是你需要的一切”。

跑 /create-verification-skill 会生成一个项目内技能，带一个驱动应用的小命令行，外加一份功能地图，说明应用里有什么、每个功能怎么触达。有了这个，智能体能证明自己的改动有效，而不是由人来当那个检查的人。

这也是编排能成立的前提，只有当每个智能体能证明自己的改动时，编排者才能安全地把工作交出去。

编排取什么形态，看工作大小。单个 issue，用 /poteto-mode 起一个智能体指向那个 issue。一个 epic，把整件事交给一个跑 /poteto-mode 的编排智能体，明确要求它当编排者，把 epic 里的每个 issue 都过一遍，把实现委派给一个智能体团队，用 GitHub 的堆叠式 PR 把工作叠起来。

[图片]

常见的编排有三种。全 Claude Code，按 epic 的复杂度由 Fable 5.1 或 Opus 5.5 当编排者，把实现分发给 Sonnet 或 Haiku 智能体。Claude Code 加本地模型，最近他让 Opus 5.5 通过 herdr 编排 Pi 里的 qwen3.8-flash-next，效果相当好。全 Pi，Pi 里跑 GPT-6.1 Sol 或 GPT-6 Astra 当编排者，委派给 Pi 里的其他 GPT 智能体，或者委派给本地跑的 qwen3.8-flash-next。

评审：六个视角，一个核实闸门

工作建好之后是代码评审。 /poteto-mode 通常把评审包含在例行流程里，他也做了自己的评审技能。 team-code-review 把改动交给六个专家智能体，每个带一个视角：

：职责和抽象是否自洽，还是有行为被重复或放错了地方。

：命名、控制流，意图是否容易跟。

：每个改动的行为是否都有有意义的覆盖面，包括失败路径和边界情况。

：耦合，以后扩展代码的代价，以及可能出现的失败模式。

：信任边界、授权、校验，以及密钥和敏感数据怎么处理。

：这次改动影响到的公开接口、安装步骤、迁移和运维手册。

让这套评审成立的是核实那一步。主智能体在汇报之前会独立核对每一条发现，打开被引用的代码，看调用方和测试，能复现就复现。推测性的、没核实的东西全部丢掉，回来的是一份不长的、有证据支撑的问题清单。

一个变体是 herdr-code-review ，它包住 team-code-review ，但通过 herdr 在一个全新的智能体会话里跑评审。评审者从干净的上下文窗口开始，而不是继承实现会话的那一个。发现的问题回到实现团队去解决，然后又是一轮评审，循环持续到工作可以提 PR 为止。评审别人的 PR 时，同一个技能可以用 conventional-comments 起草意见，前提是他自己已经看过核实过的发现并同意。

发布：干净的提交和堆叠的 PR

通过评审之后就该开 PR。两个技能在这里帮忙，都在他的 agent-skills 库里，那个库最近整合成了面向每个编程智能体的单一库。

第一个是 conventional-commits ，让每个提交遵守 Conventional Commits 规范。那套规范是在提交信息之上的一层轻量约定，用一套简单规则建立明确的提交历史，也让在其上构建自动化工具更容易，同时与 SemVer 咬合，因为它就是用提交信息来描述功能、修复和破坏性变更。一致的提交信息让人扫历史更轻松，智能体回看历史理解过去的改动时也用得上。

第二个是 stacked-prs 。当工作属于一次更大的编排，比如一个拆成很多 issue 的 epic，智能体用这个技能把改动作为 GitHub 的堆叠式 PR，通过 gh stack 命令行扩展发出去。每个 PR 装一个聚焦的改动，建立在下层那个之上，相关工作就以小的、可评审的片段排着队，避免出现巨型 PR。堆叠式 PR 在 GitHub 上还是公开预览阶段，用之前可能得先在仓库里启用。

工具会换，工作的形状不换

一年前那篇文章讲的是一个工具。现在讲三个，还得加上 herdr 把它们拢在一起，而 Damian 预计一年后再看这份名单又会不一样。

没变的是工作的形状。智能体在有好的上下文时表现依然出色，所以那些给它们喂上下文的工具，不管在哪个框架里都照样起作用。

塑形依然排第一，因为一个被充分理解的问题才是智能体能独立工作的前提。验证是他能把循环里更多环节交出去的依据，不管是智能体证明自己的改动，还是一队评审者把发现核实过之后再送到人面前，还是一摞人能真的读下去的小 PR。

[图片]

如果要从头搭自己的流程，他的建议是从循环开始而不是从工具开始。挑今天最弱的那个阶段，通常是塑形或者验证，先往那里投。问题被理解清楚、智能体能证明自己的工作之后，循环的其余部分都会变容易。
